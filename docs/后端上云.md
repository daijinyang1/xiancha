# 后端上云：Cloudflare Pages Functions + D1

> 目标：让 `xiancha.pages.dev` 的扫码结果真正落到边缘库，换设备、换浏览器也能看到同一份「扫描历史 / 数据总览」。
> 预算：0 元，只用 D1 免费额度（5 GB 存储 / 500 万次读 / 10 万次写每天）。

## 1. 为什么是这套

站点本身是 Nuxt 4 静态预渲染产物（`.out`），原来所有数据都在**构建期**从 PostgreSQL 导成 `web/app/data/*.json` 快照，再烘进 HTML。这带来两个死结：

- `/history`、`/stats` 在线上永远是 0 —— 构建时库里没有扫描记录，预渲染出来的就是 0。
- 用户扫码结果只写 `localStorage`，换手机就没了。

Pages Functions 恰好补上这一层：静态产物照旧，只在 `/api/*` 路径上挂一层边缘函数。不用起服务器、不用买数据库、和现有构建流程零冲突。

## 2. 落地结构

```
functions/
├── _lib/
│   ├── http.js                 统一 Response / 错误 / CORS / 请求体解析
│   ├── scan.js                 扫描引擎（1:1 移植 Java ScanService）
│   ├── db.js                   D1 读写（scan_log）
│   ├── catalog.js              规则 / 案例 / 证书 的内存查询
│   ├── rules.generated.js      ← 生成物，勿手改
│   ├── traps.generated.js      ← 生成物，勿手改
│   └── certs.generated.js      ← 生成物，勿手改
└── api/
    ├── health.js               GET  /api/health
    ├── stats.js                GET  /api/stats
    ├── certs.js                GET  /api/certs
    ├── rules/index.js          GET  /api/rules?type=&level=&q=
    ├── rules/[id].js           GET  /api/rules/{id}
    ├── traps/index.js          GET  /api/traps?type=
    ├── traps/[id].js           GET  /api/traps/{id}
    └── scan/
        ├── index.js            POST /api/scan
        ├── history.js          GET  /api/scan/history?limit=20
        └── stats.js            GET  /api/scan/stats
```

**路由目录的坑**：不能同时存在 `functions/api/scan.js` 和 `functions/api/scan/` 目录 —— Pages 会判定路由歧义。统一写成 `目录/index.js`。

### 数据分两条路走

| 数据 | 存在哪 | 为什么 |
|---|---|---|
| 规则 63 / 案例 12 / 证书 6 | 编译进函数（`.generated.js`） | 只读、体积小（36 KB）、零 D1 读额度消耗 |
| 扫描记录 | D1 的 `scan_log` 表 | 唯一会增长的数据 |

`.generated.js` 由 `tools/gen-functions-rules.mjs` 从 `web/app/data/*.json` 生成。**数据真源仍然是 PostgreSQL**，改完数据照旧 `node tools/db-export.mjs` 导快照，然后跑一次生成器：

```bash
node tools/gen-functions-rules.mjs          # 重新生成
node tools/gen-functions-rules.mjs --check  # 校验是否过期（CI 用，不一致退出码 1）
```

忘了跑生成器的后果：改了规则库但线上函数返回的还是旧规则。`build-site.mjs` 的构建流程里没有这一步，属于手动维护项，提交前记着跑一次 `--check`。

## 3. D1 表结构与隐私

`db/migrations/d1/V1__d1_scan_log.sql`：

```sql
CREATE TABLE IF NOT EXISTS scan_log (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at    TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  text_hash     TEXT,
  sentence_hits INTEGER NOT NULL DEFAULT 0,
  rule_hits     INTEGER NOT NULL DEFAULT 0,
  score         INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_scan_log_created ON scan_log (created_at DESC);
```

对齐 PostgreSQL 侧 `V1__schema.sql` 的 `scan_log`，只把方言换掉：`bigserial` → `INTEGER PRIMARY KEY AUTOINCREMENT`，`timestamptz` → ISO8601 UTC 的 `TEXT`。

**绝不存合同原文。** 存进去的只有 `sha256(text)` 的 64 位十六进制、命中句数、命中规则数、分数。历史页展示的就是这四个数，够用；原文一旦落库就是隐私风险，也不符合零预算（原文会让存储迅速膨胀）。

写日志失败不影响扫描返回 —— 和 Java 版 `saveLog` 的 `try/catch` 同一个取舍：用户要的是扫描结果，库挂了不该让他拿不到。

## 4. 接口契约

全部返回裸 JSON（前端 `asList` 也认 `{data|list|content|items|records}` 包装）。错误统一 `{"error": "..."}`，参数错 400、找不到 404、方法错 405、内部错 500。

### 与 Java 版的两处刻意不同

**① `POST /api/scan` 的 `level` 用 40/15 阈值，输出 `high|mid|low`**

Java `ScanService` 用的是 70/40 且输出 `"medium"`，但前端 `useApi.ts` 的 `scanLevelLabel` / `scoreToLevel` 只认 `high|mid|low`，`medium` 会被显示成「低风险」—— 80 分的合同显示成低风险，是事故级的错。统一按前端的口径来，Java 侧由 lead 同步修。

**② `GET /api/scan/history` 的 `level` 是中文 `高|中|低`**

历史页 (`web/app/pages/history.vue`) 直接拿 `level` 当徽章文字渲染，只认这三个汉字。和 `POST /api/scan` 的英文枚举不一致看着别扭，但改前端要动别人的作用域，且契约文档 (`API契约.md` 第 101 行) 本来就写的是中文。

### 扫描引擎移植要点

`functions/_lib/scan.js` 是 Java `ScanService` 的逐行移植，几个容易漏的点：

- **分句符**：`。！？\n\r` 五个，按**码点**判断（`0x3002 / 0xff01 / 0xff1f / 0x0a / 0x0d`），不能用 `String.includes` 直接比。
- **句末标点归属**：句子的 `end` 如果没到文本末尾，要 `end++` 把标点吃进来，再对首尾做 trim —— 不这么做，命中的 `sentence` 显示出来是缺标点的。
- **NBSP 不算空白**：Java 的 `\s` 不匹配 `\u00a0`(NBSP) / `\u2007` / `\u202f`，而 JS 的 `\s` 会。如果用 `\s` 做 trim，含 NBSP 的句子边界会和 Java 不一致。所以 `isJavaWhitespace` 用 `[\p{Zs}\p{Zl}\p{Zp}]` 再显式排除这三个码点。
- **空匹配防死循环**：`if (m.end() <= m.start()) continue;` 在 JS 里要改成 `pattern.lastIndex = mEnd + 1` 再 continue，否则 `lastIndex` 不前进会卡死。
- **同句合并**：key 用 `${start}:${end}`（Java 是 `(start<<32)|end` 位运算，JS 上 32 位溢出会出错，改用字符串 key）。
- **每规则上限 500 次匹配**，超了丢弃 —— 防止病态正则炸掉函数 CPU。
- **正则兼容性已核**：63 条 `regexSource` 全部 JS 可编译，无 `\Q \E \R \A \Z \p{...}` 等 Java 专有语法，`regexFlags` 全为空。

## 5. 部署与运维

### wrangler.toml

放在仓库根，只声明一个 D1 binding：

```toml
name = "xiancha"
compatibility_date = "2026-11-01"
pages_build_output_dir = ".out"

[[d1_databases]]
binding = "DB"
database_name = "xiancha-scan"
database_id = "060db997-6713-4dd2-be8e-e2479b1ad5e7"
```

不写 `account_id`（wrangler 已登录，写死换机器就崩），不写任何密钥（项目没有需要密钥的接口）。

### 建库与迁移（一次性）

```bash
node tools/deploy-worker.mjs d1-create    # 建库，已存在则只打印 id
node tools/deploy-worker.mjs d1-migrate   # 应用 db/migrations/d1/*.sql 到远端
node tools/deploy-worker.mjs d1-count     # 看远端行数
node tools/deploy-worker.mjs d1-schema    # 看远端表 / 索引
```

### 本地开发

```bash
node tools/deploy-worker.mjs dev          # http://127.0.0.1:8788/api/health
```

**不要加 `--d1=DB`。** 这个参数会让 miniflare 按 binding 名另建一个空库，跟 `d1 execute --local`（按 `wrangler.toml` 的 `database_id` 落盘）不是同一个文件，表现就是本机 `/api/scan/*` 一律报 `no such table: scan_log`。`wrangler.toml` 里已有 `[[d1_databases]]`，本地会自动读。

本机首次还要把表建进本地库：

```bash
wrangler d1 execute xiancha-scan --local --file=db/migrations/d1/V1__d1_scan_log.sql
```

### Git 集成项目的 D1 binding 要单独写

这是本次部署最容易翻车的一步。

`xiancha` 是 **Git 集成**的 Pages 项目（`daijinyang1/xiancha@main` 自动构建）。对这类项目：

- `wrangler.toml` 里的 `[[d1_databases]]` 只在**构建期**生效；
- 线上 Functions 能不能拿到 `env.DB`，看的是项目自己的 `deployment_configs` 里有没有这条 binding。

漏掉的话，`/api/health` 会返回 `{"status":"degraded","db":false}`，`/api/scan/*` 报 503。补 binding：

```bash
CF_ACCOUNT_ID=<你的 account id> node tools/bind-d1.mjs
CF_ACCOUNT_ID=<你的 account id> node tools/bind-d1.mjs --dry-run   # 只看会改什么
```

`bind-d1.mjs` 从 `wrangler.toml` 读 `database_id`（单一真源），往 `production` 和 `preview` 两份配置里写 `d1_databases.DB = { id }`，写完回读校验。

**格式坑**：`deployment_configs.production.d1_databases` 是一个**以 binding 名为键的对象** `{"DB": {"id": "..."}}`，**不是数组**。写成数组 API 会静默丢弃，回读才是空 —— 所以脚本必须回读校验，不能只看 PATCH 返回 200。

### 上线

这是 Git 集成项目，正常路径就是推 `main`：

```bash
git add functions/ db/migrations/ tools/gen-functions-rules.mjs tools/deploy-worker.mjs tools/bind-d1.mjs wrangler.toml docs/后端上云.md
git commit -m "feat: 补线上后端（Pages Functions + D1）"
git push origin main
```

推完 Pages 自动构建，40–90 秒后上线。构建命令 `node tools/build-site.mjs .out` 不变 —— `functions/` 是 Pages 自己识别的，不进 `.out`。

需要抢发（不等 Git）时：

```bash
wrangler pages deploy .out --project-name=xiancha --branch=main --commit-dirty=true
```

## 6. 验证清单

线上跑完这几条应该全绿（`<URL>` 换成 `https://xiancha.pages.dev`）：

```bash
curl -s <URL>/api/health        # {"status":"ok","db":true,"rules":63,"traps":12,"certs":6,...}
curl -s <URL>/api/stats         # rules=63 traps=12 certs=6，byType 8 类
curl -s <URL>/api/rules | head -c 100
curl -s <URL>/api/rules/R01
curl -s <URL>/api/traps
curl -s <URL>/api/certs
curl -s <URL>/api/scan/history  # []
curl -s <URL>/api/scan/stats    # total=0，last7Days 7 条

curl -s -X POST <URL>/api/scan \
  -H 'content-type: application/json' \
  -d '{"text":"公司要求我缴纳 2000 元押金，说离职返还。每天加班到 11 点没有加班费。"}'
```

POST 之后 `total` 应该从 0 变 1，`/api/scan/history` 里能看到那条记录 —— 这一步通过就说明**跨设备可见**成立（换个浏览器打开同一个地址，数字一样）。

浏览器里的判据：打开 `/history` 和 `/stats`，数字和 `curl` 一致，且页面**不出现**「后端未连接」黄条。

## 7. 边界与已知限制

- **`/api/health` 的 `uptimeSec` 不是进程运行时长。** Workers 没有常驻进程，模块顶层 `Date.now()` 在 workerd 里拿到的是 0（时钟在模块求值期被冻结），所以改成首个请求进来时惰性起算。语义是「本 isolate 处理首个请求至今」，跨 isolate 不连续，只用于判断服务活着。
- **请求体上限 128 KB**（`http.js` 的 `readJson`），scan 正文另限 50000 字符（对齐 `ScanRequest @Size(max=50000)`）。
- **D1 免费额度**：本方案每次扫描 = 1 写 + 2 读（history 查询 + stats 聚合），一天 10 万写够 10 万次扫描，远超学生项目用量。
- **扫描历史只有 7 天走势**，没有月度/年度聚合 —— 真要加，D1 侧改 SQL 就行，不用动前端。
- **`nuxt.config.ts` 不用改。** 前端 `useApi.ts` 在浏览器里走同源 `/api`（`isBrowser ? '/api' : ''`），预渲染期 `window === undefined` 故 base 为空、静默读快照，不请求也就不会画黄条，产物字节不受影响。
